# 测试与质量约束

**English** | [中文](test-and-quality.zh-CN.md) | [Español](test-and-quality.es.md)

> 本扩展靠什么判断「已经够好」：不可让渡的目标、每一级测试能看见什么、哪种证据被采信、什么条件下
> 允许合并、数字怎么记录、以及明知而携带的风险落在哪里。

## 本文档的地位

本文档是契约中「质量」的那一半。[`requirements.md`](requirements.md) 规定必须成立什么；本文档规定
如何证明它成立、什么算通过。两者冲突时以需求为准，本文档为错。

## 1. 范围与分工

| 文档 | 回答什么 |
| :--- | :--- |
| [`requirements.md`](requirements.md) | 本扩展必须做什么（按需求编号），以及不承诺什么 |
| [`build-and-verify.md`](build-and-verify.md) | 有哪些命令、各自做什么、测试布局与打包步骤 |
| [`limitations.md`](limitations.md) | 做不到什么，以及哪些从未验证过 |
| **本文档** | 怎么证明、何时可合并、证据怎么记录 |

命令写在 `build-and-verify.md`，本文档只引用。同一个命令写两处，就是文档开始对一条已变化的命令
说谎的起点。

## 2. 质量目标与硬约束

| # | 目标 | 由什么强制 |
| :--- | :--- | :--- |
| **QO-1** | **绝不修改 VS Code 本身**。不改本仓之外的任何文件，任何行为都不依赖补丁。 | 只通过七个 `CustomEditorProvider` 注册与贡献视图实现；交付物是一份只含本扩展的 VSIX |
| **QO-2** | **严格的内容安全**。webview 里的任何东西都不得加载远程资源，也不得运行没有 nonce 的内联脚本。 | 每个 webview 页面的 Strict CSP，并在页面测试中断言 |
| **QO-3** | **只读意味着没有被加载**。只读模式读取字节预算内的内容，不创建文本文档。 | 单元测试中的截断断言与「不创建文档」断言 |
| **QO-4** | **零第三方运行时依赖**。扩展宿主层是跑在自带 Node 上的纯 TypeScript。 | 清单里的依赖列表；唯一原生前置是 XAML 视图所需的 .NET 运行时 |
| **QO-5** | **平台下限是契约**。不得使用比声明的 `engines.vscode` 下限更新的 API。 | 对着下限的类型定义编译；用了更新的 API 就编不过 |
| **QO-6** | **诚实标注**。未验证的必须写成未验证。 | §10 的残余清单、`limitations.md`、以及 README 的已知限制 |

为了换一个功能而花掉上述任何一条的改动，无论测试多绿都不予接受。

## 3. 测试层级与各自能看见什么

| 层级 | 施加对象 | 能证明 | 看不见 |
| :--- | :--- | :--- | :--- |
| **T1 — 纯逻辑** | 在普通 Node 里用 mocha 跑逻辑。任何触碰编辑器 API 的东西都隔离在单独文件，好让其余部分无需实例即可测试。 | HTML 生成、CSP 文本、树构建、链接解析、配置解析、格式化、高亮 | 真实渲染；CSP 是否真的挡住了什么；第三方脚本是否真的运行 |
| **T2 — 前端产物** | 把生成的 webview 页面当数据检查 | 页面里该有的元素、nonce 与属性确实在 | 浏览器会不会拿它们做出正确的事 |
| **T3 — 真机探针** | 真实 VS Code 窗口内的一个临时自检扩展，可配置等待时间并在页面里注入 | 真实渲染、CSP 是否放行、贡献脚本是否真的执行、手势与布局行为 | 探针没有插桩的任何东西；它不在每次改动时都跑 |
| **T4 — 样例回放** | 手工或由探针打开 `demo/R<n>-*` 夹具 | 有文档的场景仍然按文档所述工作 | 没有夹具的场景 |
| **T5 — 一致性** | 对文档集做跨语言与链接检查 | 三个语言版本保持等价、没有断链 | 内容是否属实 |
| **T6 — CI** | 干净检出，单个 runner | 门禁可以从零复现 | 未使用的 runner 上的平台行为 |

决定性的盲区：**T1 跑在 jsdom 里，而 jsdom 既不执行 CSP，也不加载第三方脚本。** 因此任何关于安全
策略或贡献脚本的主张都必须走到 T3，否则就要标注为未验证。这是整张表里最重要的一条边界。

## 4. 什么算证据

| 采信 | 为什么 |
| :--- | :--- |
| 关于一次交互之后发生了什么的断言 | 行为错了它就会红 |
| 连同实测数字一起引用的探针结果 | 可以被重跑并复现 |
| 对非法配置的拒绝断言 | 解析器一旦开始接受它就会红 |
| 由 runner 打印、原文照抄的计数 | 可重算 |

| 不采信 | 为什么 |
| :--- | :--- |
| 「这条规则存在」/「这段样式被写进去了」 | 本仓已经为这个教训付过一次代价 |
| 用截图代替断言 | 不可重复，也不可比对 |
| 只说「命令退出码 0」而不给计数行 | 退出码不携带真正重要的那个数字 |
| 从旧文档里抄来的数字 | 那是记忆，不是测量 |

第二张表的第一行不是假设。曾经有一个断言只验证「某条样式规则被写进了页面」而通过，可它本该抓到的
渲染缺陷直接穿了过去。取代它的规则是：**断言场景做了什么，而不是文件说了什么**。每一个新测试都按
这句话评审。

## 5. 充分性

1. `requirements.md` 里的每条需求至少到达 §3 的某一级，且覆盖关系在 §7 点名。
2. 关于 webview 的每一类主张——渲染、内容安全、贡献脚本、手势——要么在 T3 施加过，要么在 §10 登记
   为未验证。只有 T1 的结果永远不算够。
3. 每个写在文档里的场景都有可回放的 `demo/R<n>-*` 夹具，或被明确标为没有。
4. 每个解析外部输入的部件（配置文件、工具占位符、磁盘上的 JSON）除正常路径外都配一条拒绝用例。
5. runner 报告的用例数等于设计的用例数。被跳过或静默丢弃的用例不是通过。

覆盖率百分比在这里不作为充分性判据。它无法区分「断言了结果的测试」与「仅仅执行过一行的测试」，而
本仓恰恰被这个区别咬过。

## 6. 环境

| 项 | 要求 | 说明 |
| :--- | :--- | :--- |
| Node.js | 测试栈接受的版本区间，最低支持版本在 CI 中固定 | 下限由测试所用的 DOM 实现决定，而非扩展本身 |
| VS Code | 声明的 `engines.vscode` 下限 | 真机验证时用的是更新的版本；两者都记在 `build-and-verify.md` |
| .NET | **10 Windows Desktop 运行时**，仅 XAML 视图 | 框架依赖型渲染器；其余六个视图不需要任何原生件 |
| CI runner | Windows，是刻意选的 | 若干测试契约断言 Windows 路径语义，POSIX runner 会失败，尽管扩展本身跨平台 |
| 门禁顺序 | 安装、lint、编译、测试——固定 | lint 在测试之前，因为测试命令会再编译一次，事后发现的 lint 失败会被报成测试失败 |

精确版本与命令原文由 `build-and-verify.md` 持有。本表只记录质量论证所依赖的部分。

## 8. 准入与准出

**准入。** 依赖按提交在仓库中的锁文件安装完毕，构建产物来自当前源码。测试跑的是构建产物，忘记
重新构建就等于在测昨天的代码。

**准出。** 每一步都跑，按下列顺序，不允许短路：

| 步 | 是什么 | 通过标准 |
| :--- | :--- | :--- |
| 1 | 按锁文件安装 | 完成且不改动锁文件 |
| 2 | Lint | 退出码为零 |
| 3 | 编译 | 两个阶段都成功；前端 bundle 被重新生成 |
| 4 | 测试 | 零失败，且报告的用例总数与 §9 一致 |

**不允许有条件通过。** 门禁失败就报失败，并给出步骤与计数行。没有「重跑到绿」这一步；一个已知
不稳定的测试是 §10 里的缺陷。

## 9. 记录

记录规则：

1. 数字必须能在写明的环境上、用写明的命令重算出来。否则删除而不是加限定语。
2. 一条记录带日期、运行时版本与计数输出行。
3. 数字变化时，持有它的文档必须在同一次提交里变化。

记录时间 **2026-11-06**，Node **v24.16.0**，包版本 **0.2.12**：

| Lint | `npm run lint` | 退出码为零，无发现 |
| 用例 | `npm test` | **1059 passing**，0 失败，墙钟 7 秒 |
| 测试文件 | 在源码树中计数 | **62 个测试文件** |
| 平台 | — | Windows，本地开发机 |

## 10. 缺陷与残余问题

| 等级 | 定义 | 该类的例子 |
| :--- | :--- | :--- |
| **致命** | webview 逃出内容策略，或扩展修改了自身工作区之外的状态 | 页面加载远程脚本 |
| **严重** | 可见行为错误，或某个门禁步骤没有强制它声称的东西 | 只断言「规则被写入」而非「规则生效」的测试 |
| **一般** | 行为正确，文档或记录错误 | 文档里一个过时的计数 |

未决残余问题：

| # | 问题 | 等级 | 状态 |
| :--- | :--- | :--- | :--- |
| R-1 | `build-and-verify.md` 曾携带过时计数（57 个文件 / 952 用例） | 一般 | 已关闭——在同一次改动里对齐到 §9 的数字 |
| R-2 | jsdom 不执行内容策略、不加载第三方脚本，因此 T1 无法证明任何安全主张 | 严重 | 已接受——这类主张必须走 T3，并已如此标注 |
| R-3 | XAML 渲染器是静态快照，没有数据上下文也没有消息循环；空的 Blazor 宿主是正确的，不是失败 | 严重 | 已接受——作为限制写明，不当作缺陷 |
| R-4 | CI runner 只有 Windows；POSIX 行为没有任何自动化证据 | 严重 | 已接受——在 §11 记为风险 |
| R-5 | 真机探针不在门禁内；只在 webview 改动需要时才跑 | 严重 | 已接受——T3 是刻意的动作，不是自动动作 |

R-3 与 R-4 也出现在 README 的已知限制与 `limitations.md` 中。这些清单互相矛盾时，以更严格的那条
为准，直到其中一份被改正。

## 11. 风险

| 风险 | 影响 | 当前缓解 | 未缓解部分 |
| :--- | :--- | :--- | :--- |
| 某项安全主张建立在 jsdom 之上 | 策略回归在无人察觉的情况下发布 | 凡涉及 CSP 或贡献脚本的改动都做真实窗口探针；否则该主张标注为未验证 | 探针不是自动的 |
| 路径语义在另一个平台上不同 | 非 Windows 用户遇到门禁看不见的失败 | 代码避免绝对路径，改用编辑器的 URI 处理 | 另一个平台上没有 CI |
| XAML 渲染器是外部运行时依赖 | 没有 .NET 10 Windows Desktop 时 XAML 视图完全不工作 | 渲染器作为运行时依赖随 VSIX 分发；失败会被报出而不是静默 | 运行时本身无法随包分发 |
| webview 无法把自己的资源 URL 反查成路径 | 宿主与 webview 对「是哪一个元素」产生分歧 | 宿主从文档正文重新读取路径；图片另做一次属性交叉校验 | 媒体只能按索引与类型识别，陈旧的页面可能定位错误 |
| 文档计数漂移 | 读者相信了过时的数字 | §9 的记录规则 | 依赖变更纪律；R-1 说明它确实会滑 |
| 把夹具当成测试 | 用「demo 里能跑」替代断言 | 每个场景既有 `demo/R<n>-*` 夹具，也有可测时的测试 | 人工回放终究是人工的 |

## 12. 变更协议

| 若你改动了… | 你还必须更新… | 因为… |
| :--- | :--- | :--- |
| 任何被需求覆盖的行为 | `requirements.md` 中的对应条目 | 需求是权威，本文档只负责证明 |
| 任何测试、门禁步骤或命令 | 本文档 §6、§8、§9，以及 `build-and-verify.md` | 两份文档都持有门禁，必须一起动 |
| 任何被测量的数字 | 本文档 §9 与 `build-and-verify.md` | 重复的数字会静默分叉 |
| 某个 webview 的策略或脚本加载 | 本文档 §3、§4，并补一次真实窗口探针结果 | T1 看不见这一类改动 |
| 哪些被验证、哪些没有 | 本文档 §10、`limitations.md`、README 的已知限制 | 三份清单描述的是同一批残余风险 |
| 某个样例夹具 | 本文档 §7 | 可回放证据清单是记录的一部分 |
| 本仓任何文档 | 它的中文版**与**西语版，且在同一次改动内 | 单一语言的文档就是缺陷 |

## 附录——引用结构的裁剪说明

本文档的章节骨架改编自一套 GJB 质量记录包（STP / STD / STR、型式试验、计量校准、电气安全、
9001C 设计记录集）。以下章节被整体删除，因为它们描述的是硬件交付物，对一个 VS Code 扩展没有
可观测对象：

| 被删除的章节 | 为什么不适用 |
| :--- | :--- |
| 硬件环境（温湿度、供电、机柜） | 交付物是 VSIX，运行环境是用户机器上的 VS Code |
| 型式试验、环境应力筛选、EMC 发射与敏感度 | 没有物理实体，也没有电磁发射 |
| 计量校准、溯源链、测量不确定度 | 没有测量仪器；「准确」由断言而非仪器保证 |
| 电气安全、接地、绝缘耐压 | 同上 |
| 设计评审 / 验证 / 确认 / 更改记录（9001C 8.3） | 单人维护、无独立评审方；该职责由 §8 的门禁与 §12 的变更协议承担 |
| 进度安排与人员资源（STP §5.2 / 5.3） | 没有可记录的排期与角色分工 |

被保留并改写成软件语境的是：范围、测试级别与类型、测试环境、测试项清单（§7 追踪表）、
准入与准出、需求追踪、测试记录、缺陷与失败处理、风险。

写这一节的目的，是让刻意的裁剪不被误认为缺失的章节。
